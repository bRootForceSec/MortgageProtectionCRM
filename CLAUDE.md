# Working on Mortgage Protection CRM

Read this before changing code. New features must fit the existing structure. Don't add a parallel copy of something that already exists. If what you need is missing or wrong, change the shared piece and mention it in the PR.

## What this is

- **A single-user desktop CRM.** An Electron shell (`src/desktop/`) starts a Fastify server (`src/server/`) on 127.0.0.1:5170, which serves a React UI (`src/web/`). Data lives in SQLite (better-sqlite3, WAL).
- **It ships two ways.**
  - The desktop app (Windows, Mac and Linux AppImage) updates itself from GitHub Releases.
  - The Linux systemd service (`scripts/install.sh`, `scripts/mpcrm-update.mjs`) builds from `main`. It is the owner's main Linux setup, so keep it working.
- **Every push to `main` is a release.** Keep each change small and shippable on its own, with green CI.

## Before you push

- Run `npm run typecheck`, `npm run lint` and `npm test`, and `npm run build` if you touched the build or assets.
- `npm run lint` runs oxlint (React hook rules and common mistakes) and `scripts/check-structure.mjs`. The structure check stops new SQL in route files, new silent `.catch(() => {})` in the UI, hand-written `audit_log` inserts and new `console.*` in the server. If you remove some, lower the allowance in that script as it tells you to. Never raise one to get a change through.
- Run `npm run test:e2e` for UI flows when you can.
- Write a test for new behavior. Before refactoring untested code, first add a test that pins its current behavior.
- Never commit secrets. CI runs `scripts/secret-scan.mjs`.
- Don't change user-visible behavior as a side effect of a refactor. If a change alters what the user sees, say so in the PR.

## Where things go

| You need to… | Do this |
|---|---|
| Add an endpoint | Put it in the route file for its feature (`src/server/http/*Routes.ts`). Keep the handler thin: validate input with zod, call a domain function, return the result. **No SQL in route files** (the structure check enforces it). |
| Find the route file | `importRoutes` (uploads, drafts, bulk import, import history), `leadRoutes` (leads, call list, lead page, calls and outcomes, tags, custom fields), `callingRoutes` (calling settings, outcomes, routines, rules), `numberRoutes` (caller IDs and their checks), `reportRoutes`, `dataRoutes` (export and backups), `unitrustRoutes` (what the Unitrust Firefox extension sends, and its key), `googleRoutes` (Google Calendar: your key, signing in, settings, Sync now). `app.ts` only wires these together. |
| Add business logic or queries | `src/server/domain/<feature>.ts`. Domain functions take `db` and know nothing about HTTP. Shared SQL pieces are in `db/sql.ts`: `CURRENT_OUTCOME` (a call's outcome that nothing supersedes, over `call_outcome o`), `LEAD_NAME` (over `lead l`) and `sqlList`. Use them instead of writing those out again. |
| Signal a user-facing error | `throw new DomainError(message, status?)` from `src/server/core/errors.ts`. The error handler turns it into a 4xx with `{ error }`. Don't throw a plain `Error` for user mistakes, and don't catch and rewrap errors in routes. |
| Store a setting | Use `getSetting` / `setSetting` from `src/server/core/settings.ts` (`app_setting` table). Don't create a new settings table or file. Secrets go in `Secrets` (0600 `secrets.json`), never in the DB. |
| Record who changed what | `audit(db, table, rowId, action, old, new)` from `src/server/core/audit.ts`, inside the same transaction as the change. Don't write `INSERT INTO audit_log` by hand. |
| Change the schema | Add the next numbered file in `src/server/db/migrations/`. Check open PRs first so two branches don't take the same number. Never edit a migration that has shipped. 006 is missing on purpose. Outcomes aren't schema: see the outcome row below. |
| Read config or env vars | `src/server/config.ts` (`loadConfig`). Validate there, not where the value is used. |
| Log on the server | Use the pino logger (`app.log` or `req.log`), not `console.*`. |
| Run a background job | Look at `DraftWorker`, `BulkImporter` and `PageChecker` first. A new job must stop cleanly when the server stops (`server.ts` `stop()`). |
| Call the API from the UI | `src/web/api.ts` (`api.get`, `api.post`, `api.upload`, which takes extra headers). Don't write a new fetch wrapper. |
| Show a failure in the UI | Show the user a message. Don't write `.catch(() => {})` unless failing really is harmless, and if so, add a comment saying why. |
| Load lead types in the UI | `useLeadTypes` from `src/web/leadTypes.ts`. |
| Remember a UI preference | `getStored` / `setStored` (or the `Json` versions) from `src/web/storage.ts`. Don't touch `localStorage` directly (the structure check enforces it). |
| Work with dates and time zones | Web: `src/web/when.ts` (`startOfDay`, `addDays`, `dayRange`, `todayRange`, `ymd`, and the callback parsing). Server: `domain/normalize.ts` (`timeZoneFor`). Age from a date of birth: `src/shared/age.ts` (`ageOn`). Don't write another day-range or time-zone offset helper. |
| List or pick batches | `src/web/components/BatchBrowse.tsx` (`BatchPicker`, `BatchFilterBar`, `ImportHistory`), backed by `browseImports` (`/api/imports/browse`). Filtering and grouping by bulk import live in `src/shared/batches.ts`. Don't add another plain list or dropdown of every batch. |
| Link to a lead from outside the app | `src/shared/leadLink.ts`: `http://127.0.0.1:5170/lead/<id>`, served by `leadRoutes` without the cookie. The desktop app brings its window up on the lead (`openLead` in `startServer`); a browser goes on to `#lead/<id>`, which `App.tsx` opens. |
| Change how Unitrust appointments are read | The Firefox extension is in `extension/unitrust/` (plain JS, no build; see its README). It posts to `/api/unitrust/events` with its own key, the one request that skips the cookie (`security.ts`). Storing and matching: `domain/unitrustAppointments.ts`; colors and titles: `src/shared/appointments.ts`. |
| Add or change a call outcome (either side) | Edit `OUTCOMES` in `src/shared/outcomes.ts`, and nothing else: label, side (`kind`), key, pickup, callback, booked, appointment set, appointment result, and `offered` (has a button; off keeps it working with no button, like Callback). You can rename an outcome or show/hide its button in Settings → Outcomes: that's the `outcome_overrides` setting (`saveOutcomeOverrides` in `domain/callingSettings.ts`), applied to `outcome_code.label` by `syncOutcomeCodes` and to `offered` in `/api/meta`. In the UI read `offered` from `meta.outcome_codes`, not from `OUTCOMES`. The server copies it into the `outcome_code` table when it opens the database (`db/outcomeCodes.ts`), so SQL can join on it. Never remove an outcome calls may carry; set `active: false`. Don't touch `outcome_code` in a migration (a test checks). In code, test what an outcome means (`outcomeDef(code)?.apptSet`, `BOOKED_CODES`, `sqlCodes(...)` in SQL), never its code. An appointment call logged in the app beats the Unitrust color for that appointment (`deriveLeadState`, `appointmentsOnDays`). Objections per call: `domain/objections.ts` (stored, counted in Reports by lead type); which outcomes offer the chips is `objections` in `OUTCOMES`. |
| Change policies, products or comp | Policies come from the Unitrust Business Management Report (`extension/unitrust/business.js` → `/api/unitrust/policies`) and are stored and worked out in `domain/policies.ts`. What a Unitrust status counts as and the commission formula are in `src/shared/policies.ts`. Carriers and products are rows you edit in Settings, never code: don't hard-code a carrier, product, comp hit or advance. Your comp level is the `comp_level` table (by day), not a setting. |
| Change lead statuses, Leads tabs, appointment results or funnel steps | Statuses (label, callable, timeless) and the Leads tabs: `src/shared/leadStatus.ts`. Appointment results (label, back on the list, tab, funnel steps, Unitrust color): `APPT_RESULTS` in `src/shared/appointments.ts`. Funnel step names and order: `src/shared/funnel.ts`. Use `isCallable(status)` and `sqlList(CALLABLE_STATUSES)` (`db/sql.ts`), never a hand-written `'new', 'retry', 'callback'`. Which side a lead opens on: `openingSide`. |
| Add or change a Reports card | Cards, their default order and which have a chart/table view: `REPORT_CARDS` in `src/shared/reportLayout.ts`; `ReportsPage` draws them from its `cards` map in your order (`fullLayout`). Your arrangement and saved layouts are the `report_layouts` setting (`domain/reportLayouts.ts`, `/api/reports/layouts`). A new card added to `REPORT_CARDS` shows up for everyone at the end. |
| Add or change tags on leads | `domain/tags.ts` (tables `tag` and `lead_tag`). Every tag put on or taken off a lead goes through `setTagOnLeads`, which writes a line in the lead's log (`lead_event`, kinds and sources in `src/shared/leadEvents.ts`) with what did it (`by`: you, a rule...); `lead_tag` is the tags a lead has now. Never write `lead_tag` or `lead_event` anywhere else. Making, renaming and deleting tags are audited. Filter by tag with `tag` in `LeadQuery` (a tag id, or `none`). Load tags in the UI with `useTags` from `src/web/tags.ts`. Rules and routines should add, remove and filter by tags through these, not their own tables. |
| Add or change custom fields on leads | Kinds, the form each value is kept in (`normalizeCustomValue`) and how it reads (`showCustomValue`): `src/shared/customFields.ts`. Defining fields and setting values: `domain/customFields.ts` (tables `custom_field`, `lead_custom_value`); values are saved with the lead edit (`PATCH /api/leads/:id`, `custom`) and kept in `lead_change` under the field's name. Filter with `field_id`/`field_value` in `LeadQuery`. UI: `useCustomFields` (`src/web/customFields.ts`) and `CustomFieldInput`. Rules and formulas should read and write values through these. Filters, sorting and the export read values from the view `lead_field_value`, which covers typed values and formula fields alike. |
| Add or change formula fields | The language (parser, the values and functions it offers, what Settings lists): `src/shared/formula.ts`. Turning a formula into SQL, and the `lead_field_value` view: `domain/formulas.ts`. A formula is worked out by SQLite over `lead l JOIN lead_state s`, never stored. The view is rebuilt when a formula field changes and each time the database opens. A new value is an entry in `FORMULA_VALUES` plus its SQL in `VALUE_SQL`; a new function is an entry in `FORMULA_FUNCTIONS` plus a case in `call`. A yes/no formula is a condition: `has`, `added`, `removed`, `times`, `before` and `pressed` read the lead's log (`lead_event`) and calls, so conditions over a lead's history are formulas, not new code. The formula reader also takes Python syntax (`==`, `True`, `field("Name")`, `x if t else y`, keyword arguments from `FUNCTION_PARAMS`, `#` comments). A condition is a yes/no formula: the Leads filter `where` (`conditionSql`, so rules and routine steps too), checked as you type by `checkCondition`. The condition form (`src/shared/condition.ts`: `toForm`, `toPython`; UI `ConditionEditor`) edits the same Python text; what its rows can't show stays a Python row, so add a row kind there rather than a second way to write conditions. Text in a formula goes into SQL only through `lit`. |
| Add or change statuses | A status is a named condition, never stored on the lead: shape and colors in `src/shared/statuses.ts`; saving (a rename is carried into every condition that uses it), counts, badges (`statusFlags`, `leadStatuses`) and the Leads filter (`in_status` in `LeadQuery` → `statusWhere`) in `domain/statuses.ts`; the setting is `statuses`. `status("Name")` expands to that status's condition in `conditionSql` (loops are refused) and works only in conditions and statuses, not in formula fields. UI: `useStatuses` (`src/web/statuses.ts`), `StatusesCard` and `StatusChips`. |
| Change how appointments go on Google Calendar | `domain/googleCalendar.ts` (`GoogleCalendar`: signing in with PKCE, refreshing, the sync, and its 15-minute timer, started and stopped in `server.ts`); shapes in `src/shared/googleCalendar.ts`. Which appointments go on is `upcomingAppointments`, built on `STANDING_APPOINTMENT` (`domain/appointments.ts`), the same rule as `currentAppointment`. The calendar text is `calendarTag` (`src/shared/leadLink.ts`). The event made or found for each lead is a row in `calendar_event`, so a moved appointment moves its event; nothing is deleted from the calendar. Your Google key and the sign-in are in `Secrets`; the setting is `google_calendar`. Google sends the browser back to `GOOGLE_CALLBACK_PATH`, which `security.ts` lets through without the cookie because it only finishes a sign-in the CRM started (its one-time `state`). Saving a call and a Unitrust read call `calendar.kick()`. Tests pass a fake `fetch`. |
| Add or change rules (triggers, actions) | Shapes, words and the ready-made rules: `src/shared/rules.ts` (`RuleTrigger`, `RuleAction`, `STARTER_RULES`, `describeTrigger`, `describeAction`). Storing, running, preview (runs in a transaction and rolls back) and the log (`rule_run`): `domain/rules.ts`; the setting is `rules`. Daily rules run from `RuleRunner` (started and stopped in `server.ts`); call rules run after `logManualCall`/`changeOutcome` in `leadRoutes`. A rule's leads are a `LeadQuery`, so a new filter added there works in rules too. A new action is a case in `RuleAction` and `doAction`, reusing the domain function that does it by hand. Rules on a lead's change (`tag_added`, `tag_removed`, `status`, `becomes_true`) run from `runEventRules`: after every non-GET `/api/` request (an `onSend` hook in `app.ts`, and before the answer in routes that return what a rule may change) and every minute in `RuleRunner`. Tag triggers read new `lead_event` lines (cursor setting `rule_event_cursor`); status and condition triggers keep who was in at the last check in `rule_watch`. A rule runs at most once per lead per go (the loop guard, logged as a stopped loop). A counter is a custom field of kind `counter`, changed only by the `counter` action (`setCustomValues` with `counters: true`); it reads as 0 until set. |
| Change daily routines (the order you call in) | The step and routine shapes, the starter steps and `describeFilter`: `src/shared/routines.ts`. Storing routines, today's steps and starting one: `domain/routines.ts` (settings `routines` and `routine_day`). A filter step keeps a Leads query (`LeadQuery` in `src/shared/leadFilter.ts`) with relative keys (`last_call`, `imported`, `appt_days`) that `toLeadFilter` works out when it's used, so add new relative filters there, not as fixed times. |
| Share a type or helper between server and UI | Put it in `src/shared/` and import it from both sides (server: `'../../shared/x.js'`, web: `'../shared/x'`). Code there must run in both Node and the browser: no `node:` imports and nothing from `server/`, `web/` or `desktop/` (the structure check enforces it). Response shapes not moved yet are still mirrored in `src/web/api.ts` and `src/web/importTypes.ts`; when you change one, update both sides in the same PR. |

## Data rules

- **`lead_state` is derived.** Change the source tables and rebuild (`rebuildLeadState`); never edit `lead_state` directly.
- **A lead has any number of phone numbers.** The main one is on `lead` (`phone_e164`); the rest are rows in `lead_other_phone`, in order, read and written through `domain/leadPhones.ts`. To find leads by a number, use the `lead_number` view (every number of every lead), not `lead.phone_e164` alone.
- **Outcomes are append-only.** A change adds a new outcome that supersedes the old one. Calls are voided, not deleted.
- **Health fields** (`tobacco_raw`, `health_*_raw`) are excluded from exports unless the user asks for them. Keep it that way.

## Style

- Strict TypeScript. Avoid `any` in new code.
- Import zod as `import * as z from 'zod/v4'`, like the rest of the code.
- Match the file you're in. Don't add a library for something a few lines can do, and ask before adding a dependency.
- Prefer deleting code to adding abstractions. Don't build a helper or layer with only one user.
